# Архитектура Python-приложения: слои, домен, Repository, Unit of Work, события

Этот файл нужен при проектировании приложения или модуля: где живёт бизнес-логика, как код ходит в БД и внешние сервисы, как собираются зависимости. Главный принцип: брать самую простую архитектуру, которая закрывает текущую сложность, и усложнять её по признакам, а не на будущее. Общие принципы (SOLID, связанность, границы модулей) — в скилле clean-code, здесь их форма в Python.

## 1. Выбор уровня архитектуры

| Задача | Что брать | Чего не вводить |
|---|---|---|
| Скрипт, утилита, разовая обработка | функции; решения — в чистых функциях, I/O — в тонкой оболочке | слои, классы-сервисы, порты |
| CRUD над таблицами, бизнес-правил мало | фреймворк как есть (Django, active record): толстые модели, тонкие view, чтение в одном модуле | Repository, Unit of Work, модель отдельно от ORM |
| Оркестровка расползается по эндпоинтам | сервисный слой: функция на use case поверх ORM | шину сообщений, CQRS |
| Сложные бизнес-правила и инварианты | доменная модель без ORM, агрегаты, Repository, Unit of Work | — |
| Побочные действия и интеграции «когда X, то Y» | доменные события, команды, шина сообщений | отдельное хранилище для чтения без нужды |
| Чтение сильно отличается от записи | модуль чтения на SQL, затем денормализованная модель чтения | — |

- **Не тащить доменную модель, Repository, UoW и шину в CRUD или скрипт.** Каждый слой косвенности добавляет код, маппинг и путь, по которому читатель идёт от запроса до БД. Окупается это только с ростом бизнес-логики. Если приложение — тонкая оболочка над таблицами и вряд ли вырастет, фреймворк как есть — верное решение, а не долг.
- **Поднимать уровень по признакам.** Сервисный слой — когда в view уже есть выборка из БД, проверки, обработка ошибок и commit, а число E2E-тестов растёт. Отдельная модель с Repository — когда правила модели хочется проверять без БД и они не должны зависеть от ORM. События — когда работу функции не описать без «и затем» или эксперт говорит «когда X, то Y».
- **Знать цену каждого паттерна.**
  - Repository — код на каждый новый агрегат, а от конкретной СУБД ORM отвязывает и так.
  - Unit of Work — Session SQLAlchemy уже сама UoW; откаты и вложенные транзакции даются непросто.
  - Агрегаты — новое понятие, правило «один агрегат за транзакцию», согласованность между агрегатами только в конечном счёте.
  - Шина и события — эндпоинт ждёт все обработчики; путь запроса не виден в одном месте; неочевидно, что commit отправляет письмо; возможны циклы.
  - CQRS с отдельным хранилищем сложен; обычно хватает ORM и пары методов чтения.
  - DI-фреймворк оправдан при цепочках зависимостей или внедрении во многих местах; иначе хватает словаря в bootstrap.
- **Вводить паттерны постепенно, начиная с сервисного слоя.** Это работает и поверх Django ORM. Use case сначала скопировать в новое место, потом чистить и переключать вызовы: временное дублирование допустимо.
- **Не делить систему на микросервисы ради этих паттернов.** Агрегаты, события и инверсия зависимостей управляют сложностью и в монолите. Общий код между Python-сервисами выносить сначала в пакет-библиотеку: микросервис добавляет латентность, контракт и SLA и оправдан при другом языке или независимом деплое.

## 2. Слои и направление зависимостей

- **Раскладывать код по ролям, а не по технологиям.**
  ```
  src/allocation/
      domain/          # модель, события, команды
      service_layer/   # use cases или обработчики, unit_of_work, messagebus
      adapters/        # orm, repository, клиенты внешних API, публикация событий
      entrypoints/     # HTTP, CLI, consumer брокера
      bootstrap.py
      config.py
  tests/
      unit/
      integration/
      e2e/
  ```
  Компоненты называть по назначению: `storage`, `notifications`, а не `postgres_orm`, `smtp_utils`. По коду use case не должно быть видно, какая СУБД и какой фреймворк.
- **Держать доменный код без импортов ORM, веб-фреймворка и I/O.** Библиотеки без состояния можно. Направление проверять по импортам: в `domain/` нет `sqlalchemy`, `django`, `httpx`. Плохо: доменные классы наследуют `DeclarativeBase` или `models.Model` → хорошо: таблицы в `adapters/orm.py` и классический маппинг `registry().map_imperatively(Batch, batches)`. Цена: чем дальше модель от ОО-стиля, тем труднее настроить маппинг.
- **Порт описывать `Protocol`, а не ABC.** Реализациям не нужно наследоваться, а при утиной типизации ABC легко устаревают и вводят в заблуждение. Держать порт рядом с кодом, который его использует. ABC — когда базовый класс задаёт поведение, которое подтипы обязаны сохранить.
  ```python
  class Notifications(Protocol):
      def send(self, destination: Email, message: str) -> None: ...
  ```
- **Не абстрагировать то, что неизбежно протекает.** Асинхронность проходит через все слои: если адаптеры асинхронные, use cases и UoW тоже асинхронные (`async with uow:`), без синхронных обёрток над циклом событий.
- **Публичный API слоя собирать в `__init__.py` пакета.** Это фасад в Python: клиенты импортируют из корня пакета, внутренние модули можно перестраивать.
- **Циклический импорт между слоями считать ошибкой направления.** Общее вынести в модуль ниже по дереву зависимостей. Если не выходит — передавать зависимость параметром при сборке, а не импортировать.

## 3. Доменная модель

- **Начинать с поведения и языка бизнеса, а не со схемы БД.** Имена классов, методов, исключений и тестов брать из предметной области: тест `test_allocating_to_a_batch_reduces_the_available_quantity` понятен заказчику.
- **Объект-значение делать `@dataclass(frozen=True, slots=True)`.** Равенство по значению даёт dataclass. Операции над значением — в самом типе: `Money + Money`, разные валюты — `ValueError`. Не `NamedTuple`: его можно случайно распаковать или сравнить с кортежем.
- **Сущности давать равенство и хеш по идентификатору, идентификатор делать read-only.** Чужому типу возвращать `NotImplemented`, а не `False`. Если сущность не нужна в `set` и `dict` — `__hash__ = None`. Не менять `__hash__` без `__eq__`.
  ```python
  class Batch:
      def __init__(self, reference: BatchRef, sku: Sku, quantity: Quantity) -> None:
          self._reference = reference
          self.sku = sku
          self._purchased = quantity

      @property
      def reference(self) -> BatchRef:
          return self._reference

      def __eq__(self, other: object) -> bool:
          if not isinstance(other, Batch):
              return NotImplemented
          return self._reference == other._reference

      def __hash__(self) -> int:
          return hash(self._reference)
  ```
- **Доменные значения делать своими типами.** `type Sku = str` делает контракты читаемыми, а подкласс с проверкой в `__new__` — гарантирует валидность там, где у значения есть правила.
- **Операцию, которая не принадлежит ни сущности, ни значению, писать функцией.** `allocate(line, batches) -> BatchRef` — доменный сервис. Не заворачивать глаголы в классы: `build_bar()`, а не `BarBuilder`. Доменный сервис (`calculate_tax`) — не то же, что use case сервисного слоя.
- **Доменные исключения называть на языке бизнеса.** `class OutOfStock(Exception)`, тест — `pytest.raises(OutOfStock, match="SMALL-FORK")`.
- **Хранить в модели только данные, нужные для её расчётов.** В контексте размещения `Product(sku, batches)` без цены и описания, в магазине — свой `Product`. Перевод между контекстами делать явно.
- **Ссылаться на другие агрегаты по id, а не объектом.** Плохо: `user.account.workspaces[0].documents...` через ORM — каждое свойство может ходить в БД, границы согласованности не видны → хорошо: `workspace_id: WorkspaceId`. Двунаправленная ссылка между агрегатами — признак, что границы выбраны неверно.

## 4. Агрегаты и конкурентная запись

- **Проводить границу агрегата вокруг минимума объектов, которые должны быть согласованы между собой.** Внутренние объекты менять только методами корня. Гранулярность — по инвариантам: заказы на разные SKU не конфликтуют, поэтому агрегат — `Product` по SKU, а не `Warehouse`.
- **Менять в одной транзакции один агрегат.** Если use case должен атомарно менять два — граница неверна, нужен новый агрегат. Если атомарность не обязательна — два обработчика и событие между ними. Массовую операцию делать командой на каждый агрегат.
- **Загружать агрегат целиком одним запросом и сохранять целиком.** При тысячах дочерних объектов — ленивая загрузка или другой агрегат.
- **Защищать агрегат от параллельной записи номером версии.** `version_number` увеличивать в методе агрегата, транзакции — с `REPEATABLE READ`: проигравшая падает, и операцию повторяют. Пессимистичный вариант — `with_for_update()`, при нём следить за дедлоками. Не блокировать таблицу целиком.

## 5. Repository

- **Делать репозиторий коллекцией в памяти с минимумом методов.** `add` и `get`, остальное — по нужде. `commit` в репозиторий не класть, удаление делать мягким, методом модели.
  ```python
  class ProductRepository(Protocol):
      def add(self, product: Product) -> None: ...
      def get(self, sku: Sku) -> Product | None: ...
  ```
- **Заводить один репозиторий на агрегат и возвращать из него только агрегаты.** `ProductRepository`, а не `BatchRepository`. Дополнительный поиск (`get_by_batchref`) допустим, пока возвращает агрегат. Запрос вроде `get_most_popular_products` — сигнал вынести чтение в отдельный модуль.
- **Fake писать на встроенной коллекции.** Методы однострочные, интерфейс быстро стабилизируется, поддерживать fake дёшево. Если для абстракции трудно написать fake, она слишком сложна.
  ```python
  class FakeProductRepository:
      def __init__(self, products: Collection[Product] = ()) -> None:
          self._products: MutableSet[Product] = set(products)

      def add(self, product: Product) -> None:
          self._products.add(product)

      def get(self, sku: Sku) -> Product | None:
          return next((p for p in self._products if p.sku == sku), None)
  ```

## 6. Сервисный слой и Unit of Work

- **Писать use case по одной схеме.** Открыть UoW, достать агрегат, проверить предусловия, вызвать метод модели, `commit()`. Одна функция или обработчик на use case, имя — глаголом. Cron- и фоновые задачи — тоже use cases.
  ```python
  def allocate(command: Allocate, uow: UnitOfWork) -> None:
      with uow:
          product = uow.products.get(command.sku)
          if product is None:
              raise InvalidSku(command.sku)
          product.allocate(OrderLine(command.orderid, command.sku, command.qty))
          uow.commit()
  ```
- **Принимать команду или примитивы, а не объекты модели.** Плохо: `allocate(line: OrderLine, repo, session)` → хорошо: `allocate(command: Allocate, uow)`. Точки входа и тесты не зависят от модели, а класс команды — удобное место для проверки входа.
- **Делать эндпоинт тонким адаптером.** Разобрать запрос в команду, вызвать use case или шину, доменные исключения перевести в `HTTPStatus`. Ошибки во всех точках входа обрабатывать единообразно.
- **Не вызывать use case из use case.** Работу передавать через событие, а дублирование между use cases лучше длинной цепочки вызовов. I/O (почта, файлы) делать в use case или обработчике, не в модели.
- **Unit of Work делать контекстным менеджером: коммит явный, откат по умолчанию.** `__exit__` вызывает `rollback()`: без `commit()` в БД ничего не попадёт, исключение или ранний выход оставят систему согласованной. Неявный commit в `__exit__` не делать. Сессию создавать в `__enter__` из `session_factory`, которую тесты подменяют, закрывать в `__exit__`. В async-стеке — `__aenter__`/`__aexit__`.
  ```python
  class SqlAlchemyUnitOfWork:
      def __init__(self, session_factory: Callable[[], Session]) -> None:
          self._session_factory = session_factory

      def __enter__(self) -> Self:
          self._session = self._session_factory()
          self.products = SqlAlchemyProductRepository(self._session)
          return self

      def __exit__(self, *exc_info: object) -> None:
          self._session.rollback()
          self._session.close()

      def commit(self) -> None:
          self._session.commit()
  ```
- **Не подделывать то, чем не владеешь.** Не мокать `Session` SQLAlchemy: её богатый API растаскивает доступ к данным по коду. Взамен — свой узкий `FakeUnitOfWork` с флагом `committed` и fake-репозиторием.
- **Валидацию делить на три вида.** Синтаксис (поля, типы, `qty > 0`) — на краю системы, в классе команды. Семантику (продукт существует) — предусловием в use case в том же UoW, с исключением, которое точка входа переводит в `HTTPStatus.NOT_FOUND`. Прагматику (хватит ли товара) — в модели. Защитные проверки по модели не размазывать.

## 7. События, команды и шина сообщений

- **Начинать с явного списка наблюдателей, шину вводить по признакам.** `observers: Sequence[Callable[[Order], None]]` проверяет тайпчекер, в отличие от брокера с темами-строками. Шина — когда наблюдателей приходится протаскивать через несколько уровней вызовов или побочных действий много.
- **Побочное действие не класть ни в контроллер, ни в модель, ни в use case.** `allocate`, а не `allocate_and_send_mail_if_out_of_stock`: письмо — обработчик события `OutOfStock`.
- **Событие описывать dataclass без поведения с именем в прошедшем времени, команду — в повелительном наклонении.** События — в `domain/events.py`. Агрегат складывает их в `self.events`, UoW собирает с агрегатов, которые видел репозиторий. Для той же ситуации не бросать ещё и исключение.
  ```python
  @dataclass(frozen=True, slots=True)
  class Allocate(Command):
      orderid: OrderId
      sku: Sku
      qty: Quantity


  @dataclass(frozen=True, slots=True)
  class OutOfStock(Event):
      sku: Sku


  type Message = Command | Event
  ```
- **Различать ошибки команд и событий.** У команды ровно один обработчик, её ошибка логируется и пробрасывается отправителю. Событие получают все подписчики, ошибку обработчика логируют и продолжают: письмо клиенту не должно мешать принять оплату.
- **Шину делать классом с внедрёнными обработчиками, а не модулем-синглтоном.** Реестр «тип сообщения → обработчики» и очередь: `handle(message)` вызывает обработчики и дописывает в очередь новые события из UoW. Диспетчеризация — через `match`.
  ```python
  def handle(self, message: Message) -> None:
      queue = deque([message])
      while queue:
          match current := queue.popleft():
              case Command():
                  self._handle_command(current)
              case Event():
                  self._handle_event(current)
              case _:
                  assert_never(current)
          queue.extend(self._uow.collect_new_events())
  ```
- **Делать обработчики идемпотентными.** Повторная доставка не должна повторять изменения: проверить предусловие и пропустить дубликат с записью в лог. Доставка ровно один раз невозможна; для гарантий — Outbox или брокер с журналом. Временные сбои повторять с экспоненциальной паузой (tenacity): UoW гарантирует, что каждая попытка начинается с согласованного состояния.
- **Разбиение операции на несколько транзакций считать осознанным риском.** Она может выполниться частично. Логировать каждое сообщение (repr dataclass воспроизводим в тесте), следить за сбоями и повторять.
- **Делить сервисы по процессам, а не по сущностям.** Плохо: сервисы Orders, Batches, Warehouse с CRUD API — распределённый ком грязи и каскадные отказы. Хорошо: сервис «размещение» — граница согласованности, принимает команды и публикует события.
- **Consumer брокера делать тонкой точкой входа, publisher — адаптером.** Consumer: JSON → команда → `bus.handle()`. Publisher: `json.dumps(asdict(event))`. Наружу публиковать не все внутренние события.
- **Входящие сообщения читать терпимо, исходящие проверять строго.** Брать нужные поля, лишние игнорировать, не разбирать структуру чужих идентификаторов. Определения сообщений между сервисами не делить, схему событий версионировать.

## 8. Чтение

- **Чтение держать в отдельном модуле `views.py`.** Модель оптимизирована для записи: чтение через репозиторий тянет в неё лишние методы и фильтрацию в Python. Для чтения нормален прямой SQL, а если читаются те же сущности — ORM.
- **Команду не заставлять возвращать данные для показа.** POST меняет состояние и отвечает `HTTPStatus.ACCEPTED`, результат читается через GET. Шина не возвращает результаты обработчиков.
- **На чтении допускать устаревшие данные, при записи проверять текущее состояние.** Данные устаревают сразу после загрузки страницы.
- **Денормализованную модель чтения обновлять обработчиками событий, а не триггерами БД.** `Allocated` → `add_allocation_to_read_model`. Если она сломалась, пересобрать её тем же обработчиком.
- **Сложное чтение делить на загрузку данных и построение представления.** Построитель тестируется на списках словарей.

## 9. Зависимости и сборка приложения

- **Объявлять зависимости параметрами, а не подменять импорт через `mock.patch`.** Патч нужен в каждом тесте с побочным эффектом и ломается от безобидного `import email` → `from email import send`.
  ```python
  # плохо
  def notify_out_of_stock(event: OutOfStock) -> None:
      email.send(STOCK_TEAM, f"Out of stock: {event.sku}")

  # хорошо
  def notify_out_of_stock(event: OutOfStock, notifications: Notifications) -> None:
      notifications.send(STOCK_TEAM, f"Out of stock: {event.sku}")
  ```
- **Собирать приложение в одном `bootstrap.py`.** Он объявляет зависимости по умолчанию с возможностью подменить, выполняет разовую инициализацию (маппинг ORM, логирование), внедряет зависимости в обработчики и возвращает готовую шину. Точки входа вызывают только `bootstrap()`, тесты — его же с подменами.
- **Не создавать зависимость в значении параметра по умолчанию.** `uow=SqlAlchemyUnitOfWork()` в сигнатуре выполняется при импорте модуля. Писать `None` и создавать внутри.
  ```python
  def bootstrap(
      *,
      start_orm: bool = True,
      uow: UnitOfWork | None = None,
      notifications: Notifications | None = None,
  ) -> MessageBus:
      if uow is None:
          uow = SqlAlchemyUnitOfWork(session_factory())
      if notifications is None:
          notifications = EmailNotifications(get_smtp_settings())
      if start_orm:
          start_mappers()
      command_handlers = {Allocate: partial(allocate, uow=uow)}
      event_handlers = {
          OutOfStock: [partial(notify_out_of_stock, notifications=notifications)],
      }
      return MessageBus(
          uow=uow,
          command_handlers=command_handlers,
          event_handlers=event_handlers,
      )
  ```
- **Внедрять зависимости в обработчик через `functools.partial`, замыкание или класс с `__call__`.** Не lambda: позднее связывание путает, если зависимость меняется, а traceback менее понятен. Автоматический подбор по `inspect.signature` — это уже свой DI-фреймворк.
- **Простую зависимость передавать `Callable`, сложную — портом.** `publish: Callable[[Channel, Event], None]`. Для порта: протокол, реальная реализация, fake для unit-тестов и интеграционный тест реальной реализации против «менее поддельного» сервиса (например, MailHog в docker-compose).
- **Не держать изменяемое состояние в глобальном объекте.** Глобальная шина с очередью небезопасна при потоках и мешает тестам. Веб-приложение создавать фабрикой (application factory).
- **Конфигурацию читать функциями из окружения в одном модуле.** `get_postgres_uri()`, а не константа на импорте: тесты могут менять окружение. Значение по умолчанию — для локальной разработки, или ошибка, если дефолт небезопасен. Импортировать конфиг только в bootstrap и тестах.

## 10. Расширяемость и подключаемый код

- **Ставить точки расширения только там, где изменения ожидаются.** Каждая абстракция ухудшает чтение и отладку. Признак, что пора: «хирургия дробовиком» — новый вариант требует правок во многих файлах, а новый параметр протаскивается через всех вызывающих.
- **Независимые оси изменений разносить по типам с одной точкой входа.** Вид уведомления — union dataclass-ов, способ доставки — свой union, маршрут — данные. Код предметной области вызывает только `send_notification(NewSpecial(...))`. Разбор union — `match` с `assert_never`: тайпчекер потребует обработать новый вариант, а словарь-таблица эту проверку теряет.
  ```python
  type Notification = NewSpecial | IngredientsOutOfStock


  def render(notification: Notification) -> str:
      match notification:
          case NewSpecial(dish=dish):
              return f"New special: {dish}"
          case IngredientsOutOfStock(ingredients=ingredients):
              return f"Out of stock: {', '.join(ingredients)}"
          case _:
              assert_never(notification)
  ```
- **Бизнес-правило не должно импортировать чужое бизнес-правило ради кусочка механизма.** Механизм (повтор, кэш, таймаут) выделить отдельно и подключать декоратором, стратегии передавать функциями — правила об этом в `SKILL.md`.
- **Не реализовывать паттерны, встроенные в язык.** Синглтон — объект на уровне модуля. Фабрика — функция или класс, переданный параметром. Итератор — генератор. Фасад — `__init__.py` пакета. Имя паттерна в имя класса не включать: `EnhancedQuery`, а не `EnhancedQueryDecorator`.
- **Адаптер стороннего класса писать композицией.** Плохо: `class UserSource(UsernameLookup)` — чужие методы и ложное «является» → хорошо: хранить `UsernameLookup` в поле и вызывать его методы.
- **Состояния с правилами переходов делать объектами, а `Enum` оставлять для состояний-данных.** Каждое состояние реализует переходы и бросает `InvalidTransitionError` на запрещённый. Пустую реакцию писать явным методом.
- **Плагины из других пакетов регистрировать через entry points и проверять при загрузке.** Регистрация — `[project.entry-points."app.plugins"]` в `pyproject.toml`, загрузка — `importlib.metadata.entry_points(group="app.plugins")` (3.10+). Интерфейс описать `Protocol`: тайпчекер не видит, что зарегистрированный класс ему соответствует, а `runtime_checkable` проверяет только имена атрибутов.

## 11. Тестирование по слоям

| Слой | Сколько тестов | Чем |
|---|---|---|
| Сервисный слой или шина | основная масса | fake UoW, fake-репозиторий, fake-адаптеры; проверка конечного состояния |
| Доменная модель | ядро: сложные правила, начало проекта | чистые объекты; удалять, когда их покрыл сервисный слой |
| Адаптеры: репозиторий, UoW, клиенты | интеграционные | реальная БД того же движка, что в продакшене; «менее поддельный» сервис |
| Точки входа | один E2E на фичу и один на все неуспешные пути | через API, данные со случайными id |

- **Готовить данные в тестах через use cases, а не через объекты модели или SQL.** `bus.handle(CreateBatch(...))`, затем `bus.handle(Allocate(...))`. Если тесту сервисного слоя приходится лезть в домен, сервисный слой неполон.
- **Собирать тестовую шину тем же `bootstrap` с подменами.** `bootstrap(start_orm=False, uow=FakeUnitOfWork(), notifications=FakeNotifications())`.
- **Транзакции и конкурентную запись проверять на реальной БД.** Два случая UoW: без `commit` — откат, исключение — откат. Конкурентность — двумя потоками: версия выросла на 1, ровно одна ошибка.

Fakes против моков, изоляция, тесты async-кода — в `testing.md`.

## 12. Существующий проект

- **В Django начинать с малого.** Завести `logic.py` в каждом app для логики вне форм, view и моделей, собрать чтения в одно место, сервисный слой ввести при дублировании. Модули логики не привязывать к иерархии apps. Толстые модели годятся, пока логика несложная и тесты быстрые.
- **Цену Repository и UoW в Django оценить до начала.** Классического маппинга нет: нужны ручные `to_domain()` и `update_from_domain()`, а UoW сохраняет агрегаты вручную. Django admin обходит инварианты модели.
- **Легаси заменять через Strangler.** Старая система публикует события, новая строит по ним свою модель и постепенно забирает работу. Начинать с «ходячего скелета», который принимает событие и пишет его в лог.

## Чек-лист

1. Уровень архитектуры соответствует сложности: нет Repository, UoW и шины в CRUD или скрипте?
2. Доменный код не импортирует ORM, веб-фреймворк и клиенты I/O?
3. Порты описаны `Protocol` и у каждого есть простой fake?
4. Эндпоинты тонкие: разбор запроса, вызов use case, перевод доменных ошибок в `HTTPStatus`?
5. Use case меняет один агрегат в одной транзакции, а commit явный?
6. Побочные действия вынесены в обработчики событий, а обработчики идемпотентны?
7. Зависимости передаются параметрами и собираются в одном bootstrap, без создания в дефолтах и глобального состояния?
8. Точки расширения стоят только там, где изменения уже случались или объявлены?
9. Основная масса тестов — на сервисном слое с fakes, а E2E — по одному на фичу?
