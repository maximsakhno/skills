# Тестирование Python-кода

Файл нужен перед тем, как писать, править или ревьюить тесты, в любом проекте и с любым фреймворком. Главный принцип: тест проверяет поведение через публичный интерфейс и падает, только когда это поведение сломано. Быстрыми тесты делает архитектура: логика отделена от ввода-вывода, на границе — фейки, а не моки.

Если в проекте pytest, прочитать ещё `pytest.md`: там pytest-реализация этих правил с учётом его версии. Общие правила рефакторинга, характеризационных тестов и работы с кодом без тестов — в скилле clean-code.

## 1. Уровни тестов и стратегия

- **Строить пирамиду: много быстрых тестов логики, меньше интеграционных, минимум сквозных.** Быстрые тесты покрывают всю бизнес-логику без БД и сети. Интеграционный тест проверяет только стык своего кода с внешней системой: репозиторий с БД, адаптер с API. Сквозной (E2E) — один на сценарий пользователя: он доказывает, что всё связано, но медленный, хрупкий и не показывает, где ошибка.
- **По умолчанию тестировать через сервисный слой (use cases), а не через внутренние классы.** Каждая строка теста фиксирует форму кода, и тесты внутренних классов мешают их рефакторингу. Тесты модели писать для сложных правил и в начале работы, а затем удалять, если их покрыли тесты уровнем выше. Если сервисного слоя нет, тестировать через API под интерфейсом, а сам интерфейс (HTTP, CLI) проверять тонко: верно ли он вызывает API и что выводит.
- **Не проверять одно и то же на двух уровнях; краевые случаи — на нижнем.** Сквозной тест — для основного пути и связки частей. Все неуспешные пути закрывает один сквозной тест обработки ошибок, остальное — быстрые тесты. Краевой баг, найденный сквозным тестом, воспроизвести быстрым тестом уровнем ниже; сквозной тест падает при зелёных быстрых — значит, у какого-то поведения нет быстрого теста.
- **Считать число тестов по связности частей, а не по произведению вариантов.** 3 кузова × 3 двигателя × 3 цвета — не 27 тестов: покраска зависит от кузова и не зависит от двигателя, хватит 3 + 3. При комбинаторном взрыве между слоями: успешный и неуспешный путь — тестами верхнего слоя, все комбинации — тестами нижнего.
- **Держать быстрый набор таким, чтобы его можно было гонять после каждого шага.** Медленный набор начинают пропускать. Если он замедлился до десятков секунд, пересмотреть архитектуру: логику — из-под БД, ввод-вывод — за фейки.
- **Раскладывать тесты по уровням в отдельные каталоги и уметь запускать каждый.** `tests/unit`, `tests/integration`, `tests/e2e`; тестовый файл — на модуль кода. Во время работы запускать один тест или файл, перед сдачей — весь набор, быстрые первыми.

## 2. Что проверять

- **Проверять поведение, а не реализацию.** Для запроса — возвращённый результат, для команды — публичный побочный эффект: запись в хранилище, отправленное сообщение, ответ. Тест внутреннего вызова или имени шаблона ломается от эквивалентной переделки и пропускает пустой результат. Плохо: `send` вызвал `_format_body` → хорошо: тело отправленного письма.
- **Каждой ветке — свой тест.** Каждый `if` и каждый `try/except` — ещё тест. Пример для `authenticate`: нет токена → `None`; токен есть, пользователя нет → создан новый; пользователь есть → возвращён существующий.
- **Подбирать данные по классам эквивалентности и границам.** Один представитель на класс, без дублей из одного класса. На границу — три теста `<`, `=`, `>`: они ловят перепутанные `<` и `<=`. Отдельно — пустая и полная структура, ноль, 29 февраля, переход года.
- **Добавлять в данные «постороннего», чтобы не прошла ленивая реализация.** Второй список, элементы которого не должны попасть в ответ; второй пользователь, чтобы не прошло «взять первого». Защищаться от случайной ошибки, а не от умышленной.
- **Проверять свойство, а не случайное конкретное значение.** Плохо: `assert menu == [Meal("Spring Roll", 120), ...]` ломается при добавлении блюда → хорошо: в меню есть закуска, салат и второе, сумма калорий меньше лимита. Для сгенерированного id — что у двух объектов они разные.
- **Невалидный ввод проверять тремя отдельными тестами.** Ничего не сохранено (ловит запись до валидации), ответ правильный, ошибка видна пользователю.
- **Проверять пути ошибок, отказы внешних систем и права, а не только успешный путь.** Неверный тип даёт `TypeError`, недопустимое значение — `ValueError` или доменное исключение. Упавший почтовый сервер не роняет заказ, пользователь не видит чужое. У исключения проверять и тип, и сообщение: иначе тест пройдёт от случайного исключения того же типа.
- **Не тестировать константы, фреймворк и чужие библиотеки.** `assert TIMEOUT == 3` ничего не проверяет, «сохранить и прочитать через ORM» проверяет ORM. Чужой код проверять до своей границы: что его вызвали с правильными аргументами.
- **Структурированный вывод разбирать, а не сравнивать строкой.** JSON — через `json.loads`, HTML — парсером; проверять только значимое (`action` формы, `name` полей).
- **Неочевидное решение закреплять отдельным тестом.** `test_email_is_primary_key` объяснит будущему читателю, почему так сделано. То, что не должно падать, проверять явно, с комментарием: `make_list(owner=None)  # не бросает`. В остальных случаях тест без проверки результата — антипаттерн.

## 3. Структура и имена

- **Разделять подготовку, действие и проверку (arrange/act/assert) пустыми строками.** Действие — 1–2 строки. Комментарии `# given`/`# when`/`# then` — только если из кода не видно, зачем нужна подготовка.

```python
def test_allocating_to_a_batch_reduces_the_available_quantity() -> None:
    batch = Batch(ref=BatchRef("batch-001"), sku=Sku("SMALL-TABLE"), qty=20)
    line = OrderLine(order_id=OrderId("order-123"), sku=Sku("SMALL-TABLE"), qty=2)

    batch.allocate(line)

    assert batch.available_quantity == 18
```

- **Один сценарий — один тест; новое требование — новый тест, а не ещё один assert в старом.** Если первый assert упадёт, о следующих ничего не узнать, и одна ошибка скроет другую. Несколько assert допустимы, если они проверяют одно свойство. Монолитный тест дробить через хелпер действия, а не копипастой.

```python
# плохо: test_invalid_input проверяет и хранилище, и статус, и текст ошибки
# хорошо: хелпер post_empty_item(client) и три теста
def test_empty_item_is_not_saved(client: Client, repo: FakeRepository) -> None:
    post_empty_item(client)

    assert repo.list_all() == []
```

- **Называть тест фразой о поведении на языке предметной области.** Имя — документация требования, его должен понять заказчик. Плохо: `test_allocate_2` → хорошо: `test_prefers_warehouse_stock_to_shipments`.
- **Держать подготовку короткой: общее — в хелперы и фикстуры, в тесте только отличие.** Плохо: 15 одинаковых строк в каждом тесте → хорошо: `add_base_ingredients()` и одна строка с отличием. Большая подготовка — сигнал, что у самого кода сложные зависимости.
- **Не доводить DRY в тестах до предела.** По тесту должно быть видно, чем он отличается от соседей; немного повторения лучше хелпера, за которым не видно данных.
- **Одинаковые тесты с разными данными оформлять таблицей случаев, не больше 3–4 параметров.** Больше параметров делают тест слишком общим. Один набор — один сценарий.
- **Переиспользовать в тестах константы сообщений из кода.** `EMPTY_ITEM_ERROR`, а не повторённый текст.
- **Аннотировать тесты и хелперы (`-> None`) и проверять их тайпчекером так же строго, как код.** Тело функции без аннотаций mypy по умолчанию не проверяет.

## 4. Сообщения о падении

- **Видеть каждый новый тест красным и читать сообщение.** Сломать код (вернуть не то, переставить аргументы) и убедиться, что тест падает по нужной причине с понятным текстом. Если после замены куска кода на заведомо неверный все тесты зелёные — не хватает теста.
- **Сравнивать объект целиком одним assert, а не по полям.** Diff покажет все отличия сразу; порядок побочных эффектов — список действий фейка целиком. Недетерминированное поле подставить из результата: `assert saved == replace(expected, id=saved.id)`. Плохо: `assert equivalent(a, b)` — при падении видно только `False`.
- **Писать простой assert, а не «умный».** Плохо: `assert any(row.text == "1: Buy" for row in rows)` → хорошо: `assert "1: Buy" in [row.text for row in rows]` — при падении видно, что было на самом деле. Не проверять распаковкой: `[form] = page.forms` падает с невнятным `not enough values to unpack`.
- **Давать объектам предметной области читаемые `__repr__` и `__eq__`.** Dataclass даёт оба. `<Item object at 0x...>` в сообщении бесполезен; ленивые коллекции и запросы ORM приводить к `list` перед сравнением.
- **Повторяющуюся сложную проверку выносить в хелпер, который сам объясняет несоответствие.** Проверка «блюдо веганское» перечисляет не-веганские ингредиенты, а не возвращает `False`.

## 5. Тестовые данные

- **Создавать данные кодом с говорящими именами, а не загружать из JSON-фикстур.** Файл с данными трудно поддерживать при смене схемы, по нему не видно, какие значения важны, а какие — заполнитель, и со временем его копируют ради мелких отличий. Фабрика с умолчаниями показывает в тесте только важное: `make_order(qty=0)`.
- **Готовить состояние через use cases, а не через внутренние объекты или SQL.** Плохо: `FakeRepository([Batch(...)])` → хорошо: `bus.handle(CreateBatch(...))`, затем `bus.handle(Allocate(...))`. Если тесту сервисного слоя приходится лезть в модель, сервисный слой неполон. Сквозные тесты готовить через публичный API.
- **Общие данные делать неизменяемыми.** `tuple` и frozen dataclass не дадут одному тесту испортить данные другого; изменяемое создавать заново для каждого теста.
- **В тестах против общего внешнего окружения изолировать данные уникальными идентификаторами.** `random_sku()` на `uuid4` вместо очистки БД. Почтовые адреса — `@example.com`.

## 6. Изоляция и детерминизм

- **Делать тесты независимыми от порядка и прошлых запусков.** Состояние сбрасывать перед каждым тестом. Падение только при определённом порядке указывает на общий ресурс: дать ему одного владельца.
- **Очистку ставить в гарантированный механизм, а не после assert.** `cleanup()` после упавшего assert не выполнится. Использовать `try/finally`, контекстный менеджер или механизм фреймворка и регистрировать очистку сразу после создания ресурса.
- **Дорогой ресурс поднимать один раз, а изоляцию давать дешёвым сбросом перед каждым тестом.** Подключение к БД — на модуль или сессию, перед тестом — очистка таблиц или откат транзакции.
- **Не трогать реальное окружение.** Файлы — во временном каталоге, а не в `~` пользователя или текущем каталоге. Переменные окружения и глобальные настройки менять механизмом, который откатит их после теста. Лучше всего передать путь или настройку параметром.
- **Время, случайность и генерацию id передавать зависимостью, а не патчить.** `datetime.now` не патчится: `datetime` — C-тип. Часы — keyword-only параметр, в тесте — фиксированное время. `datetime.utcnow()` устарел (3.12): `datetime.now(UTC)`.

```python
# плохо: внутри вызывается datetime.now(), тесту приходится патчить модуль
# хорошо
def is_expired(token: Token, *, now: Callable[[], datetime] = lambda: datetime.now(UTC)) -> bool:
    return token.expires_at <= now()


def test_token_expires_at_deadline() -> None:
    token = make_token(expires_at=NOON)

    assert is_expired(token, now=lambda: NOON)
```

- **Не выполнять работу при импорте модуля.** Подключения и чтение конфига при загрузке зависят от порядка импорта; оборачивать их в функцию инициализации, которую явно вызывают и прод, и тест.
- **Ждать асинхронный результат опросом с таймаутом, а не `sleep`.** `sleep` либо слишком короткий (ложные падения), либо слишком длинный. Цикл ловит ожидаемые исключения до срока и перебрасывает последнее, чтобы причина попала в traceback. Сначала проверять то, чего не было в старом состоянии, иначе assert пройдёт до обновления.

```python
def wait_for[T](check: Callable[[], T], *, timeout: float = 5.0) -> T:
    deadline = monotonic() + timeout
    while True:
        try:
            return check()
        except AssertionError:
            if monotonic() > deadline:
                raise
            sleep(0.1)
```

- **Не мириться с нестабильными тестами.** Найти причину — гонку, общее состояние, время, порядок — и сделать тест детерминированным. Для разбора сохранять снимок состояния при падении, для воспроизведения — гонять тест многократно.

## 7. Фейки, моки и граница системы

- **Предпочитать реальные объекты и фейки и проверять конечное состояние, а не вызовы.** Fake — рабочая упрощённая реализация (репозиторий на `dict`), mock — объект, записывающий вызовы. Моки связывают тест с реализацией: проверка `messages.success.call_args` падает, когда код переходит на эквивалентный `add_message(...)`. Фейк на встроенной коллекции — несколько строк:

```python
class FakeRepository:
    def __init__(self, products: Collection[Product] = ()) -> None:
        self._products: MutableMapping[Sku, Product] = {p.sku: p for p in products}

    def add(self, product: Product) -> None:
        self._products[product.sku] = product

    def get(self, sku: Sku) -> Product | None:
        return self._products.get(sku)
```

- **Отделять решения от ввода-вывода, чтобы логику тестировать вообще без двойников.** Плохо: `sync()` сам обходит диски и копирует файлы, тестам нужны временные каталоги → хорошо: чистая `determine_actions(src_hashes, dst_hashes)` возвращает список действий и тестируется на словарях, а тонкую оболочку покрывают один-два интеграционных теста.
- **Мокать только внешние побочные эффекты и выбор реализации, который сам является требованием.** Внешнее — почта, платёж, чужой HTTP API: мок не даёт слать письма и показывает аргументы. Мок-тест на выбор реализации оправдан, когда важно, какой механизм вызван (аутентификация фреймворка, а не своя). Если у фреймворка есть тестовый двойник (in-memory почтовый ящик), брать его.
- **Не подделывать то, чем не владеешь.** Плохо: мок `Session` SQLAlchemy или `requests` — их широкий API расползается по тестам → хорошо: свой узкий адаптер (`UnitOfWork`, `Notifier`), фейк для тестов логики и интеграционный тест самого адаптера.
- **Передавать зависимость параметром, а не патчить её по строке.** Много `patch("pkg.module.name")` ради одного теста — запах: патч по строке ломается при переносе модуля и прячет зависимость. Если для абстракции трудно написать фейк, она слишком сложна — упростить интерфейс.

```python
# плохо: BuildStatus.notify сам вызывает requests.post, тест патчит "ci.status.requests.post"
# хорошо
class BuildStatus:
    def __init__(self, transport: Transport) -> None:
        self._transport = transport


def test_notify_sends_build_status() -> None:
    transport = FakeTransport()

    BuildStatus(transport).notify(build_id=BuildId("42"), status=Status.OK)

    assert transport.sent == [Payload(build_id=BuildId("42"), status="ok")]
```

- **Мок создавать только со спецификацией.** `create_autospec(Gateway, instance=True)`, `Mock(spec=Gateway)`, `patch(..., autospec=True)`. Без спецификации опечатка в имени метода или неверная сигнатура повторяются в коде и тесте незамеченными, а опечатка вроде `asssert_called_with` молча проходит.
- **Патчить имя там, где его ищет тестируемый код, и только откатываемым средством.** При `from os import getcwd` в `app.files` патчить `app.files.getcwd`, а не `os.getcwd`. Присваивание `module.name = fake` не откатывается и ломает следующие тесты — нужен `patch` как контекстный менеджер или механизм фреймворка. Встроенные `open` и `compile` не патчить.
- **Вызовы сравнивать явно и только те, что не видны по результату.** `assert gateway.charge.call_args_list == [call(order_id, amount)]` при падении показывает фактические вызовы. Нерелевантные аргументы — `ANY`: лучше недоопределить тест, чем переопределить. Результат зависимости задавать в подготовке (`gateway.charge.return_value = receipt`) и сверять с ним. Проверку вызова и проверку вывода держать в разных тестах.
- **В быстрых тестах запрещать сеть глобально.** Общая подмена сетевого клиента, падающая при вызове, ловит случайно не подменённый вызов.

## 8. Тесты слоёв приложения

- **Модель предметной области тестировать без двойников и на языке бизнеса.** Это чистые объекты; доменные исключения проверять по типу и тексту: `OutOfStock` с `SMALL-FORK` в сообщении.
- **Сервисный слой тестировать с фейковыми репозиторием и Unit of Work.** На вход — примитивы или команды, а не объекты модели. Фейковый UoW отмечает коммит, тест проверяет и состояние, и сам коммит.

```python
class FakeUnitOfWork(UnitOfWork):
    def __init__(self) -> None:
        self.products = FakeRepository()
        self.committed = False

    def commit(self) -> None:
        self.committed = True


def test_allocate_commits() -> None:
    uow = FakeUnitOfWork()
    services.add_batch(
        ref=BatchRef("b1"),
        sku=Sku("LAMP"),
        qty=100,
        uow=uow,
    )

    services.allocate(
        order_id=OrderId("o1"),
        sku=Sku("LAMP"),
        qty=10,
        uow=uow,
    )

    assert uow.committed
```

- **Тестовое приложение собирать тем же кодом сборки, что прод, подставляя фейки.** Быстрые тесты — тот же bootstrap с фейками, интеграционные — с реальным UoW на тестовой БД.

```python
bus = bootstrap(
    start_orm=False,
    uow=FakeUnitOfWork(),
    notifications=FakeNotifications(),
    publish=lambda *args: None,
)
```

- **Обработчики событий тестировать через настоящую шину, фейковую шину брать только для сложной цепочки событий.** Тогда проверять, какие сообщения обработчик породил.
- **Репозиторий проверять интеграционным тестом на реальной БД.** Сохранить через репозиторий — прочитать сырым SQL, и наоборот. `__eq__` сущности часто сравнивает только id, поэтому атрибуты и вложенные коллекции проверять явно. На однотипные классы хватит одного теста «сохранить и прочитать».
- **Транзакции и конкурентность проверять на том же движке БД, что в проде.** У UoW два обязательных случая: без `commit` изменений нет, при исключении — откат. Конкурентность — двумя потоками на реальной БД: ровно одна ошибка конфликта, версия выросла на 1. Потоки синхронизировать примитивами (`Barrier`, `Event`), а не `sleep`.
- **Реалистичность теста внешней интеграции выбирать по цене.** Для почты обычно хватает smoke «отправка не падает» и быстрых тестов содержимого письма; реальный ящик медленный и хрупкий. Протокол, проверенный годами, заново не тестировать.
- **Сложный обработчик запроса (view, endpoint) считать запахом.** Если для него нужно много тестов, логику вынести в сервисный слой без фреймворка и тестировать там.

## 9. Async-код

- **Убедиться, что тест действительно выполняет корутину.** Вызов `async def` без `await` только создаёт объект корутины: тест пройдёт, ничего не проверив. Async-тест запускать раннером с поддержкой async (в pytest — плагином, см. `pytest.md`).
- **Объекты, привязанные к циклу событий, создавать внутри цикла теста.** `Lock`, `Event`, `Queue`, клиенты и пулы, созданные на уровне модуля или в общей подготовке и переиспользованные в другом цикле, падают с «attached to a different loop».
- **Ограничивать каждое ожидание в тесте сроком.** Зависшая корутина должна ронять тест, а не вешать набор: `async with timeout(1):` (3.11+), в более старой версии — `wait_for`.
- **Ждать событие, а не время.** Вместо `await sleep(0.5)` в надежде, что фоновая задача успела, ждать `Event`, результат задачи или очередь — со сроком.
- **Гонки проверять множеством конкурентных задач.** Ошибка возникает, когда состояние читают до `await`, а пишут после: 100 задач с `tmp = counter; await sleep(0); counter = tmp + 1` дают 1 вместо 100. Тест запускает задачи через `TaskGroup` или `gather` и проверяет итог.
- **Медленные внешние сервисы заменять async-фейками с тем же интерфейсом.** Методы фейка сразу возвращают результат или бросают заданное исключение: так проверяются таймауты и ошибки без сети.
- **Непонятные зависания и медленные шаги разбирать в отладочном режиме asyncio.** `python -X dev` или `PYTHONASYNCIODEBUG=1` пишут в лог корутины, которые так и не дождались, и шаги дольше 100 мс, блокирующие цикл.

## 10. Property-based и мутационное тестирование

- **Генерировать входные данные (Hypothesis), где у функции есть свойство, верное на всём домене.** `@given(integers(min_value=900))` сразу нашёл `calories=0`, который руками никто не выбрал. Домен сужать параметрами стратегии или `assume(...)`, найденную регрессию закреплять `@example(...)`. Свои объекты — `builds(Dish, ...)` или `@composite`.

```python
@given(limit=integers(min_value=900))
@example(limit=5001)
def test_meal_plan_fits_calorie_limit(limit: int) -> None:
    plan = make_meal_plan(Calories(limit))

    assert sum(meal.calories for meal in plan.meals) <= limit
```

- **Объект с инвариантами и последовательностью операций проверять stateful-машиной.** `RuleBasedStateMachine`: `@rule` — шаг со сгенерированными аргументами, `@invariant` — проверка после каждого шага. Hypothesis сам сократит падающую последовательность.
- **Оценивать силу тестов мутациями (mutmut).** Выживший мутант (`<` → `<=`, `continue` → `break`, `0` → `1`) — пропущенная проверка: дописать тест на границу или удалить ненужную строку.

## 11. Когда тестов достаточно

- **Использовать покрытие как поиск слепых зон, а не как цель.** Смотреть непокрытые строки и ветки, включив покрытие ветвей: `"even" if n % 2 == 0 else "odd"` даёт 100 % строк одним тестом. Непокрытый код может оказаться ненужным — тогда удалить его.
- **Считать тесты достаточными, когда поломка любой строки логики роняет хотя бы один тест.** У каждой ветки и `except` есть тест, границы проверены с обеих сторон, пути ошибок покрыты. Тесты вида `assert result is not None` при 100 % покрытия ничего не гарантируют.
- **Удалять тесты, потерявшие ценность, вместе с кодом.** Тесты-проверки понимания чужого API (ORM, библиотеки) — после появления тестов своего адаптера, тесты модели — когда их покрыл сервисный слой.

## 12. Изменение кода под тестами

- **Писать тест до кода и видеть ожидаемое падение.** Тест должен упасть там и так, как предсказано; ошибка импорта ещё не написанного имени тоже ожидаема. Затем — минимальное изменение под текущую ошибку. Если тест позволяет захардкодить ответ, добавить второй пример.
- **За шаг менять либо код, либо тесты.** Если переписать тест и код одновременно, не видно, проверяет ли тест прежнее поведение.
- **Перенося логику между слоями, сначала добавить тест уровнем выше.** Убедиться, что при поломке падают оба, перенести логику, удалить ставшие ненужными тесты нижнего уровня. Высокоуровневые тесты допускают больше рефакторинга.
- **Незаконченное выключать видимо и снимать до сдачи.** Пропуск с причиной, видимый в отчёте, а не закомментированный тест или переименование в `DONT_test_`. Перед сдачей просмотреть diff на оставленные пропуски.
- **Не прятать за пропуском тест, упавший из-за неверного понимания API.** Переписать тест по контракту. Пропуск и «ожидаемое падение» — только для ещё не сделанного.
- **При регрессии сначала вернуться к зелёному самым быстрым путём.** Не дописывать новое поверх красных тестов. Найденное важное поведение закрепить отдельным тестом.

## 13. unittest

- **Брать специализированные assert-методы.** `assertEqual`, `assertIn`, `assertIsNone` дают понятное сообщение, а `assertTrue(x in y)` выводит только `False is not true`. В unittest голый `assert` хуже `assertEqual`.
- **Таблицу случаев прогонять через `with self.subTest(case=...)`.** Каждое падение видно отдельно.
- **Ресурс освобождать через `self.addCleanup(...)` сразу после его создания.** Очистка выполнится, даже если дальнейшая подготовка или тест упадут. Общий сброс состояния — в `setUp`.
- **Исключения, предупреждения и float проверять специальными средствами.** `with self.assertRaises(OutOfStock) as cm:` и проверка `cm.exception` после блока; предупреждения — `assertWarns` или `warnings.catch_warnings(record=True)`; float — `assertAlmostEqual(..., places=...)` или `delta=`.
- **Держать `__init__.py` в `tests/` и его подкаталогах.** Без него `unittest discover` может найти 0 тестов. Пропуск — `@skip("причина")`, незаконченный тест — `self.fail("Finish the test")`.

## Чек-лист

1. Тест проверяет поведение через публичный интерфейс, а не внутренние вызовы и не константы?
2. Выбран самый низкий уровень, на котором видно поведение, и оно не проверяется дважды?
3. У каждой ветки, границы и пути ошибки есть свой тест, а в данных есть «посторонний»?
4. Один сценарий на тест, подготовка, действие и проверка разделены, имя описывает поведение?
5. Тест был красным, и сообщение о падении понятно без отладчика?
6. Двойники — фейки или моки со спецификацией только на внешней границе, зависимость передана параметром, а не пропатчена по строке?
7. Тест не зависит от порядка, текущего времени, сети и реальных файлов, а очистка гарантирована?
8. Async-тест действительно выполняет корутину и ждёт событий со сроком, а не `sleep`?
9. Нет пропусков без причины, тестов без проверки результата и тестов, потерявших ценность?
